# Solid melee effects regression checks

Run `scripts/test-solid-melee.ps1 -GameDir <game>` after building. Supply optional `-BloodFxDll <BloodFX.dll> -BloodFxConfig <com.apoca.bloodfx.cfg>` to exercise an installed BloodFX build in the isolated host. The script copies those inputs into its owned test directory; it does not install or modify either mod. Reports, exact input hashes and logs are in `artifacts/solid-melee-<RunName>`.

Supply `-WildWastelandDll <WildWasteland.dll>` for additional optional metal-setting checks against the actual companion assembly and fixture-owned config entries. Production reads only the entries in memory; tests do not change personal companion settings. Latest spark correction: 80 checks standalone, 90 with WW, 96 with WW and BloodFX. The earlier C87 candidate failed the author's live size/car test; 13 corresponding baseline assertions fail, and the corrected routing/clone scaling passes. Native Vehicle/vehPart/vehPartRemoved ancestry covers painted bodies/doors without guessing from paint names. Glass, wheels, upholstery, wood/ground and flesh retain their separate routes. Shared source scale/particle modules stay unchanged. A same-host rerun verifies explicit fixture config initialization prevents stale NaN test values. Actual rendered size and drivable-car results remain pending a new live test.

## Results, 2026-10-18

The prior candidate failed 12 of 43 native checks. The corrected public candidate passed all 43 with BloodFX 0.2.0 and the current copied settings, and all 37 without BloodFX. The staged local development build passed the same 43 checks. Both builds compiled with zero errors; the public build retained six existing serialization-field warnings, and the development build retained twelve.

These cases run the production `ProcessHit`, LMB `SwingContact`, RMB `CuttingContact`, real Unity collider queries, actual PlayMaker `FsmFloatAdd` body-part damage and the real optional BloodFX `Scan`/`Poll` implementation. They cover living bodies, specific body-part triggers, physical corpse meshes/boxes, dead health with a residual damage receiver, ordinary hard surfaces, single-contact damage/effects, dynamic native prefab value/action replacement, disabled native effects and replacement of a destroyed native source. The test invokes BloodFX's polling explicitly for observation; production code does not invoke its private methods.

The corpse regression was in the pack: its flesh classification required a living-style Health hierarchy. Native physical `*_Dead` ragdolls can lack that hierarchy, so a hit selected the ordinary surface effect. Residual corpse Bodypart components could also receive another Damage event. The corrected shared solid-contact snapshot separates flesh feedback from damage eligibility before native events can destroy the target. Native prefab choices are read from the current small wrench FSM on contact instead of being permanently copied after the first hit. One pack native effect is emitted per accepted solid contact. Flamethrower damage emits no pack blood spray.

The broader reported BloodFX failure also affected the stock machete in the author's October 17 session. The pack's unchanged native damage already produced a single BloodFX response when its real polling ran in the isolated host. BloodFX 0.2.0 watches root health values; it does not replace the wrench's effect assets or expose a public hit API. Its installed SHA-256 was `13AB800FBF77760A45341AE8F6F218206478151437DF3D2CA990A417B343BD3B`. That session's log contained its startup message but no scan/watch messages. This does not prove why its live Update stopped or whether its host was destroyed. No global workaround, private runtime API bridge or third-party edit was made.

Full rendered combat, BloodFX's automatic update lifecycle in the user's complete mod collection, scene transitions and the exact packaged release remain unverified by these synchronous native fixtures. Do not describe the broader BloodFX issue as fixed by the solid-contact change.

## Metal impact follow-up, 2026-10-18

The author's machete/motorcycle video shows an additional native metal impact. The base machete and wrench both reference MeleeHit_Effect; Wild Wasteland's melee CreateObject patch substitutes the game's MetalImpact prefab for car metal. The pack's direct Instantiate path bypasses that patch.

Chainsaw contacts now classify the current collider/material before damage and select the shared native MetalImpact on metal. Flesh takes priority; glass, tyres, wood and ground retain their previous effect routes. One owned effect is emitted per accepted contact and the metal effect is removed after four seconds. The native surface effect's deliberately cleared value remains disabled, including on metal. No Wild Wasteland API or file is required or modified. Changes made to the shared native prefab are used when cloning it.

The preceding candidate fails five metal-routing checks. A review caught an intermediate version bypassing an explicit native-effect disable; its one-check failure was reproduced and corrected. The merged build passes 59 checks with the actual BloodFX DLL/config and 53 without it. Production LMB/RMB routing, flesh priority, material/physics classification, wheel/pane exclusions, one-effect routing and asset-missing fallback are exercised. Fixture objects now occupy an explicit valid scene: objects made during early Awake otherwise looked like invalid-scene assets and produced a misleading lookup result. The cold host has no real MetalImpact asset loaded; source lookup and rendered sparks in a loaded world remain **NOT VERIFIED**. Synthetic source selection is not described as a rendered test.

The author confirmed fuel operation and damage to car occupants in the previous installed candidate. They also confirmed that BloodFX remains absent. The configured G diagnostic key produced no dump or BloodFX hit log. This supports investigating the separate mod's runtime/input handler, but does not prove the cause. No third-party runtime patch or fix is claimed.

Subsequent authorized live diagnostics established that BloodFX's original native Unity component is destroyed by the time the Game scene runs, while its managed instance/config remain. Three unpaused observations show unchanged initial scan timer, no tracked enemies and no gushes despite enabled switches. Its Update and key handling therefore cannot run. The destroyer and exact earlier timing are not established. This is a separate BloodFX lifecycle defect; no repair or new pack dependency is included.
